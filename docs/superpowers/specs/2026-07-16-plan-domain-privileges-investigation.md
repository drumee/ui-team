# Plan ↔ Domain/Organisation Privileges — Investigation & Implementation Plan

> Generated 2026-07-16 on branch `feat/plan-domain-privileges` — multi-agent investigation across
> `schemas`, `server-team`, `loby`, `ui-team`, `admin-api`, `admin-console`, `onboarding-ui`,
> against the target model in <https://docs.drumee.com/technology/yellow-pages-schema>.

## Target model (docs + product owner)

- Signup → default domain (`domain.name = app.drumee.com`, `domain_id = 1`) = **FREE** plan.
- Upgrade **PRO** → `domain_id` stays `1` (entitlement only).
- Upgrade **TEAM / ENTERPRISE** → prompt user for a **subdomain** → create organisation URL; `domain_id` changes.
- The **paying user becomes organisation owner** via `yp.privilege` (NB: canonical table is the British-spelled `yp.organisation`).
- Organisation services declared in ACL with `scope: "domain"`.
- Org creation sequence: `domain_create` → `domain_grant(dom_owner)` → create `organisation` row.

## Current state (end-to-end)

SIGNUP: loby signup.create_account (loby/service/signup.js:288-342 → lib/loby.js:46-123) builds a profile with NO domain and calls yp proc drumate_create (schemas/yellow_page/procedures/drumate/drumate_create.sql:49-79), which resolves the default domain from get_sysconf('domain_name') with a hardcoded fallback to domain_id=1, writes drumate.domain_id, a yp.privilege row {uid, domain_id, privilege=1 (dom_member)}, entity.dom_id, and a personal vhost '<username>-u.<main_domain>'. So every new user lands on the default domain (app.drumee.com = id 1) as dom_member — this half matches the target. PLAN/ENTITLEMENT: canonical store is yp.quota (domain_id PK, payer_id UNIQUE, plan, quota JSON + source/period_end patch), read through a 4-tier cascade (payer → domain>1 → legacy drumate.profile.$.quota → seeded free row payer 'ffffffffffffffff') in disk_limit/disk_free/my_disk_limit. Catalog = yp.plan seed: free/pro (entity_type user), team (org, per-seat), storage_100/500/1000 + pro_seat (addon) — NO enterprise row anywhere. BILLING: FE settings_billing (ui-team billing/index.js) renders free/pro/team/enterprise cards priced from SERVICE.payment.catalog, and _proceedToCheckout (lines 555-585) posts SERVICE.payment.checkout with entity_type = plan==='team' ? 'org' : 'user' (enterprise falls to 'user'), then redirects to hosted Stripe Checkout — with NO subdomain prompt anywhere in the flow. payment.checkout (server-team/service/private/payment.js:38-118) for entity_type 'org' REQUIRES a pre-existing organisation owned by the caller (payment_get_org → NOT_ORG_OWNER), so a Free user buying Team dead-ends. The Stripe webhook (server-team/service/public/stripe_webhook.js:222-369) does idempotency (stripe_event_seen/processed/delete), mirrors into subscription_new (subscription_update), and upserts entitlement into yp.quota (payment_apply_entitlement — org rows keyed by organisation.domain_id ×seats, user rows keyed by payer with domain unchanged), then WS notify 'payment.plan_updated' → Visitor.respawn refreshes quota in the UI. It NEVER creates a domain/organisation and never writes yp.privilege. PRO upgrade via this path correctly keeps domain_id=1 (entitlement-only) — matching the target — but a contradictory legacy path is still live: drumate.hub_to_pro (server-team drumate.js:43-90, ACL scope hub/owner) does domain_create → domain_grant(dom_owner) → organisation_add → drumate_hub_to_pro, i.e. PRO = own domain + org, the pre-Stripe semantics. ORG CREATION: the target sequence exists end-to-end but only as a billing-disconnected admin path: adminpanel.create_organisation (admin-api/service/adminpanel.js:2172-2205, ACL scope hub/owner) = guards (already_in_other_domain, ident_exists) → quota-row pre-check (payer_id=uid AND domain_id=1, else INVALID_SUBSCRIPTION) → domain_create(ident) → domain_grant(domain.id, Remit.dom_owner, uid) → organisation_add → update_quota re-keys the payer's quota row to the new domain. Its FE is organization_form (ui-team settings/organization/form) — the only subdomain prompt in the product (name + ident + '.{main_domain}' suffix, yp.host_exists check, then create_organisation + location.reload) — reachable only from the Pro-gated 'My seats' tab (when Visitor.domain_id==1) and a legacy contextmenu 'Pricing' item; a TEAM buyer is never routed to it, and a free user CAN reach it without paying via 'pricing' (though the quota pre-check then rejects). Three more near-duplicate org-creation paths exist: loby plan.upgrade, adminpanel.organisation_add (legacy, my_subscription-gated, still called by admin-console's domain-page), and dead unregistered copies in server-team organization.js/role.js. PRIVILEGES/ACL: yp.privilege is {uid, domain_id, privilege int, is_authoritative} but with UNIQUE KEY(uid) — one row per user TOTAL, so membership is single-domain and domain_grant's ON DUPLICATE KEY UPDATE silently MOVES the user between domains (it also updates drumate.domain_id, vhost.dom_id, entity.dom_id — 4 statements, NO transaction). Remit tiers (dom_owner=63…dom_member=1) live only in JS (@drumee/server-essentials lex/remit.js); the yp.remit table is dormant/unseeded, and move_user_to_free hardcodes 63. ACL enforcement matches the target where wired: acl/*.json scope:'domain' → server-core acl.js check_domain (tenant equality user.domain_id vs hub org_id/domain_id, then SQL function domain_permission(uid, dom_id, mask) = privilege & perm); 82 scope:'domain' services exist — 73 in the admin-api plugin (admin.json 30 + adminpanel.json 43), 9 legacy server-ops in server-team; payment.* services are all scope hub/owner. UI state: Visitor carries domain_id/domain/org_id/privilege/quota from yp.get_env at bootstrap (drumee.js init_globals); plan identity everywhere = Visitor.quota().plan; the only post-org-creation refresh is location.reload(). onboarding-ui has no org/subdomain step (steps are profile analytics). Naming: yp.organisation (British) is canonical — organisation.domain_id UNIQUE (1:1 org↔domain), owner_id UNIQUE (one org per owner, relied on by payment_get_org); legacy twins linger (organization table, domains, subscription vs subscription_new vs quota, product vs plan).

## Implementation plan

### 1. Re-key yp.privilege to per-domain rights  
**Repo:** `schemas` — **depends on:** none — foundation for everything else; decide open question #1 first (single vs multi membership)

Patch (yellow_page/patches/, additive per schemas layout rules): drop UNIQUE KEY `uid` on yp.privilege, add UNIQUE KEY (uid, domain_id). Update domain_grant to upsert on (uid,domain_id) and decide policy for the old domain-1 row (keep as dormant membership or delete). Audit every reader that assumes one-row-per-user: my_organisation, domain_permission (must filter by dom_id — it already does), domain_privilege, move_user_to_free. Backfill: existing rows are already one-per-user so the migration is a pure key change; deploy via patches/manifest.txt + bin/patch-from-file.

### 2. Make domain provisioning atomic: one transactional proc org_provision(ident, name, payer_uid)  
**Repo:** `schemas` — **depends on:** step 1

New proc yellow_page/procedures/organization/ (British 'organisation_*' naming — CAVEAT: the canonical table/procs are spelled organisAtion; never grep-replace to American spelling, the 'organization' table is a dead legacy twin). Wrap in START TRANSACTION: ident_exists/vhost_exists guard → domain_create(ident) (keep '.'+main_domain() suffix) → domain_grant(domain_id, 63 /*dom_owner — seed yp.remit or a constant table so 63 stops being JS-only*/, payer_uid) → organisation row + entity type 'organization' + yp.hub serial row + vhost(fqdn=link) (fold in organisation_add's body; drop its legacy 30-day subscription insert) → COMMIT with rollback on error so no orphaned domain rows. Also wrap domain_grant's own 4 statements in a transaction. Standardize the org-hub FQDN convention (pick one of the three: ensure_vhost dash-join vs unique_hostname vs organisation.link) inside this proc.

### 3. Add enterprise to the catalog + fix entitlement semantics  
**Repo:** `schemas` — **depends on:** open question #2 (enterprise pricing/quota); parallel with step 2

yp.plan seed patch: add 'enterprise' rows (entity_type 'org', period month/year, currency, stripe_price_id, quota JSON per product decision). Extend payment_apply_entitlement's org branch to cover enterprise (seats × quota). Retire/repair my_subscription (references non-existent subscription.uid) — replace its consumers with a quota/plan read (yp.quota.plan for payer) so org gating uses Stripe-era truth.

### 4. New pre-checkout validation service payment.validate_org_ident  
**Repo:** `server-team` — **depends on:** none

Validates {ident, name}: Validator.host, yp ident_exists + vhost_exists + already_in_other_domain (Visitor domain_id>1 → reject), returns normalized fqdn `${ident}.${main_domain}`. Reuse existing helpers (memory note: check service/lib + @drumee/server-core/essentials before writing new ones).

### 5. Checkout carries the subdomain; webhook provisions the org  
**Repo:** `server-team` — **depends on:** steps 2, 3, 4; open question #3 (prompt before checkout vs after payment)

payment.js checkout: for entity_type 'org' (team AND enterprise), if payment_get_org returns no org, accept {ident, name} in the payload (re-validate via step 4 logic) and thread them into Stripe session metadata alongside {entity_type, entity_id, plan, period} instead of erroring NOT_ORG_OWNER. stripe_webhook.js checkout.session.completed branch (lines ~244-293): when metadata.entity_type==='org' and payer has no organisation, call the new transactional org_provision(ident, name, payer_uid) BEFORE payment_apply_entitlement (which already keys org quota by organisation.domain_id); reuse admin-api create_organisation's update_quota prior art to move any domain-1 quota row. Keep notify_user('payment.plan_updated') and add the new domain/privilege to the payload so the FE can transition. PRO path: no change — entity_type 'user' keeps domain_id=1 (already correct).

### 6. Retire the legacy PRO=own-domain path and reconcile duplicates  
**Repo:** `server-team` — **depends on:** step 5 live

Deprecate drumate.hub_to_pro (remove from acl/drumate.json or gate behind a feature flag) so PRO never creates a domain; delete the dead unregistered organization.js/role.js organisation_add copies; deprecate loby plan.upgrade (loby repo) or reduce it to a thin wrapper over org_provision. ## Open questions (product decisions required before implementation)

1. Membership cardinality: should the privilege re-key to (uid,domain_id) enable true multi-domain membership (user keeps a domain-1 row AND an org row), or stay move-semantics (one active domain, row migrates)? This decides whether drumate.domain_id remains the single 'current tenant' pointer and how my_organisation/check_domain behave.
2. Enterprise plan definition: pricing model (per-seat like team? custom contract?), quota JSON, Stripe price/product IDs, and whether self-serve checkout is allowed at all or 'Contact sales' remains the UI path with backend-provisioned orgs.
3. Subdomain prompt timing: collect the subdomain BEFORE Stripe checkout (metadata-threaded, webhook provisions — risk: ident squatted between checkout and webhook, needs reservation or re-check) or AFTER payment success (post-return interstitial — risk: paid users stuck on domain 1 until they complete it; needs the 'team plan but domain_id==1' nag). The plan supports both; pick the primary.
4. What happens to the payer's existing content on TEAM upgrade: do their personal hubs move into the new org domain (drumate_hub_to_pro-style rewrite of hub vhosts/domain_id) or stay on domain 1? The legacy path moved everything; the target model is silent.
5. Fate of the legacy PRO=own-domain users: accounts already on private domains via hub_to_pro — grandfather them, or migrate them back to domain 1 with entitlement-only PRO (move_user_to_free-style but preserving paid quota)?
6. Downgrade semantics for TEAM→PRO/FREE: is move_user_to_free (transfer/abandon hubs, everyone → domain 1) the intended behavior, and who inherits org hubs when the org domain is dissolved vs merely unpaid (payment_clear_entitlement currently keeps the domain, drops quota)?
7. Canonical org-hub FQDN convention: 'host-domain' (ensure_vhost dash), 'host-ident.main_domain' (unique_hostname), or 'host.organisation.link' (hub_to_pro)? Existing vhost rows follow all three.
8. Can the free 'pricing'/seats org-creation path survive at all, or must org creation strictly require a paid team/enterprise entitlement (quota-row gate) — i.e., is admin-side org provisioning without payment (support/enterprise onboarding) a supported backdoor and under which ACL?
9. Should yp.remit be seeded and made the SQL-side authority for tier values (and lex/permission.js's conflicting dom_* aliases renamed), or do tiers stay JS-only constants?
10. One org per owner (organisation.owner_id UNIQUE) — keep this invariant? It underpins payment_get_org; relaxing it breaks the checkout→org resolution and the webhook idempotency check.
11. Is the British 'organisation' spelling frozen as the permanent canonical (docs say yes)? Confirm before any cleanup renames, and confirm the 'organization' legacy table can be dropped in prod (needs a data audit — report found zero proc refs but not zero data).

## Appendix — per-repo investigation reports

### ui-team billing/plan/organization surfaces vs target yp domain-tenant model

Billing UI (settings_billing) renders a 4-plan catalog (free/pro/team/enterprise) priced from SERVICE.payment.catalog with hardcoded fallbacks, and checks out via SERVICE.payment.checkout with entity_type="org" for team — but NO subdomain/organization-URL prompt exists anywhere in the checkout flow. A subdomain prompt DOES exist (organization_form: name + ident input + ".{main_domain}" suffix → yp.host_exists → adminpanel.create_organisation → location.reload) but it is a disconnected legacy surface reachable only from the Pro-gated settings_account "My seats" tab (when Visitor.get('domain_id')==1) and a hardcoded contextmenu "Pricing" item — it never participates in the TEAM purchase. Plan display everywhere reads Visitor.quota().plan (entitlement), post-payment state arrives via WS "payment.plan_updated" → Visitor.respawn + ?checkout=success return modal (settings_billing_result → payment.checkout_result). Organization global (ui-core letc/organization.js) is set once at bootstrap from yp.get_env; UI reads domain_id, url, privilege (bitmask vs _K.permission.*), useEmail, metadata. Visitor carries domain_id, domain, org_id, privilege (domainCan = privilege & permission) and quota {plan, total_seat, storage, billing_cycle}.

**Gaps:**
- TEAM purchase never prompts for a subdomain: _proceedToCheckout (billing/index.js:555-585) posts entity_type:'org' straight to SERVICE.payment.checkout and redirects to Stripe; the checkout skeleton (checkout.js:163-167) has plan pills + seats/storage/cycle only — no organization-URL/name field anywhere in the flow. Target model requires prompting the paying user for a subdomain before/at TEAM upgrade.
- The only subdomain prompt (organization_form) is orphaned from billing: it calls SERVICE.adminpanel.create_organisation (not the payment pipeline), is mounted only via (a) settings_account 'My seats' tab — gated by canAdmin() which requires plan==='pro' exactly (/^pro$/i, settings/account/index.js:40) — and (b) a legacy contextmenu 'Pricing' item. ### schemas (yp / yellow_page): domain-tenant model, org creation, privilege/remit, plan-quota-billing procs

yp DB matches the docs' single-table-inheritance model: entity (type enum organization/hub/drumate..., dom_id) + subtype tables drumate/hub/organisation, with domain (id,name UNIQUE) as tenant pivot and vhost (fqdn→id,dom_id) as FQDN mapping. organisation.domain_id and owner_id are both UNIQUE (strict 1:1 org↔domain and one org per owner). Membership is drumate.domain_id == organisation.domain_id, granted by domain_grant which upserts yp.privilege and rewrites drumate.domain_id + vhost.dom_id + entity.dom_id (4 statements, NO transaction). Signup lands on domain_id=1 via drumate_create's fallback chain (privilege default 1 = dom_member). PLAN/QUOTA today is canonical in yp.quota (domain_id PK, payer_id UNIQUE, quota JSON + source/period_end via patch), read through a 4-tier cascade (payer → domain>1 → legacy drumate.profile.quota → free row payer 'ffffffffffffffff') in disk_limit/disk_free/my_disk_limit; catalog = yp.plan (plan_code × entity_type user/org/addon × period × currency → stripe_price_id + quota JSON). The Stripe flow (server-team stripe_webhook.js/payment.js) calls stripe_event_seen/processed/delete, subscription_update/remove (→ subscription_new), payment_apply_entitlement/clear_entitlement, payment_get_{payer,org,plan,addon,catalog,subscription}. Remit tier values (dom_owner=63, dom_admin=31, dom_admin_security=15, dom_member=1) exist ONLY in JS (@drumee/server-essentials lex/remit.js); SQL stores raw ints and the yp.remit table is dormant/unseeded. Domain-switch procs: domain_grant, drumate_change_domain, drumate_hub_to_pro, move_user_to_free; subdomain vhost creation: domain_create (+ .main_domain() suffix), ensure_vhost, unique_hostname, organisation_create/organisation_add, desk_create_hub.

**Gaps:**
- privilege table is UNIQUE KEY(uid) not (uid,domain_id) — target model says per-user PER-DOMAIN rights; today a user can belong to exactly one domain, and domain_grant's ON DUPLICATE KEY UPDATE silently destroys any previous domain membership. Multi-domain (e.g. FREE default + TEAM org) is structurally impossible without a key change.
- domain_grant is NOT atomic: 4 separate statements (privilege upsert + drumate/vhost/entity updates) with no START TRANSACTION — a mid-proc failure leaves dom_id columns inconsistent. Target describes it as atomic.
- PRO upgrade divergence: target says PRO keeps domain_id=1 (entitlement-only, via yp.quota). The new Stripe path (payment_apply_entitlement entity_type='user') conforms, but the still-live legacy path drumate_hub_to_pro + server drumate.js hub_to_pro creates a domain+organisation on PRO upgrade and moves the user's domain — two contradictory PRO semantics coexist.
- TEAM/ENTERPRISE flow gap: no proc implements 'prompt for SUBDOMAIN → domain_create → domain_grant(dom_owner) → organisation row' as one unit tied to payment. organisation_create (transactional) never calls domain_grant — when it creates a fresh domain the paying owner gets NO yp.privilege row and drumate.domain_id stays unmoved; the correct 3-step sequence exists only in server JS (organization.js add(), non-transactional, using the older organisation_add). stripe_webhook.js never creates domains/orgs at all — org must pre-exist (payment_get_org) before a team checkout.
- Remit tiers (dom_owner=63 etc.) are not mirrored in SQL: domain_grant takes a raw TINYINT, move_user_to_free hardcodes 63, and the yp.remit table (method→level) is dormant with no seed and no readers — there is no SQL-side symbolic-permission mapping for the ACL engine to consult; symbolic→mask resolution happens only in JS.
- org gating still reads legacy billing: organization.js add()/my_privilege gate on my_subscription proc, which references a non-existent subscription.uid column (broken); the Stripe-era truth (yp.quota.$.organization / plan entitlement) is not consulted for 'may this user create an org'.
- Legacy twins linger un-reconciled: organization vs organisation tables, domains vs domain, subscription vs subscription_new vs renewal*, product vs plan, drumate.profile.$.quota (tier-3) vs yp.quota — the target model implies organisation/domain/plan/quota are canonical but nothing migrates or drops the twins.
- privilege.is_authoritative is never written by any proc (domain_grant ignores it) — dead column relative to the documented model.
- entity.dom_id DEFAULT NULL while vhost.dom_id DEFAULT 1 — pool/factory entities have NULL dom_id until activation; any tenant-equality ACL check must handle NULL, and organisation_delete's DELETE FROM entity WHERE dom_id=_domain_id relies on activation having stamped it.
- Subdomain shape inconsistency for org-domain hubs: ensure_vhost builds 'host-domain' (dash) for domain_id>1 while unique_hostname builds 'host-ident.main_domain' and drumate_hub_to_pro rewrites to 'host.organisation.link' — three different FQDN conventions for the same concept.
